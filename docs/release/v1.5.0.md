### Sortable UUIDs (v6 & v7)

The headline of this release is **UUID v7** — standardised in [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html) in 2024, and now the default recommendation for database primary keys.

A v7 leads with a 48-bit Unix millisecond timestamp followed by 74 random bits. Because the time comes first, string and byte ordering both match creation order — so inserts land at the end of a B-tree index instead of scattering across it the way v4 does. It's a drop-in replacement for v4 that's friendlier to your indexes, with no configuration or coordination required.

```bash
idgen -t uuid7               # 019f6b81-95bd-7c63-a046-b0741dddbed3
idgen -t uuid7 -c 5 | sort   # already in order
```

**UUID v6** is also supported. It's v1's fields with the timestamp reordered most-significant-first, so it sorts too. It exists mainly as a migration path for existing v1 data — for new systems, prefer v7.

```bash
idgen -t uuid6               # 1f181298-9620-6519-b560-4dff09331797
```

Both work with every output format (`-f hyphenated|simple|urn`), and `inspect` reads their embedded timestamps back:

```bash
$ idgen inspect 017F22E2-79B0-7CC3-98C4-DC0C0C07398F
Type: UUID
Version: SortRand
Variant: RFC4122
Timestamp: 2022-02-22T19:22:22+00:00
```

`idgen` now covers 11 ID types: UUID v1/v3/v4/v5/v6/v7, NanoID, CUID v1/v2, ULID, and MongoDB ObjectID.

### Apple Silicon binaries

This release is the first to ship a native `idgen-macos-arm64` binary. Previously only an Intel build was published, so Apple Silicon Macs had to fall back to Rosetta — and the Homebrew formula pointed at an arm64 asset that was never built, which made it uninstallable.

### Colourised help

`--help` and error output are now colourised in a terminal, and plain everywhere else. Detection is automatic: colour is emitted only when stdout is an interactive terminal, so CI logs, `| less`, and `> file` all stay clean. `NO_COLOR`, `CLICOLOR`, `CLICOLOR_FORCE`, and `TERM=dumb` are all honoured. Generated IDs themselves are never colourised — they're the payload.

### Bug Fixes

**UUID v1 used a hardcoded node ID.** *This changes generated output — see Behaviour Change below.*

The node field exists to separate two hosts that generate a UUID in the same 100-nanosecond tick. It was hardcoded to `01:02:03:04:05:06`, meaning every user of this tool shared the same node ID, leaving the clock sequence as the only defence against cross-host collision. It's now a random per-process node ID with the multicast bit set, per RFC 9562 §5.1, so it can never collide with a real IEEE 802 MAC address.

**`inspect` only extracted timestamps for v1.** Timestamp extraction was gated on UUID v1 specifically, so a v7 — the version whose entire purpose is its embedded time — reported no timestamp at all. It now reports timestamps for v1, v6, and v7. *(Fixed by @lcdss in #4.)*

**Tests located the binary via Cargo internals.** The integration tests derived the binary path by walking up from the test executable and assuming a fixed `target/` layout. That breaks under `build.build-dir` (Cargo 1.91+) and the upcoming build-dir layout changes. They now use `CARGO_BIN_EXE_idgen`. This only affects contributors running the test suite, not users. *(Reported by @epage in #2, found via a rustc crater run.)*

### Behaviour Change

**UUID v1 output has changed.** v1 UUIDs now carry a random per-process node field instead of the fixed `01:02:03:04:05:06`. If you have stored v1 UUIDs generated by earlier versions of `idgen`, the node segment (the last 12 hex digits) will no longer match what this version produces.

This is a fix, not a regression — the old behaviour undermined the uniqueness guarantee v1 is supposed to provide. But it's a real change to emitted output, which is why this is a minor release rather than a patch. No CLI flags, formats, or exit codes changed, so nothing else needs updating.

UUID v6 shares v1's node field and uses the same corrected node ID.

### Internal

- Release and publish scripts are now idempotent, derive all names from `Cargo.toml` and the release workflow rather than hardcoding them, and no longer run `cargo update` at release time (which meant the shipped lockfile had never been tested). Documented in `docs/RELEASING.md`.
- Added `.gitattributes` pinning text files to LF, preventing whole-file CRLF rewrites on Windows.
